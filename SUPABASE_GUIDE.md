# Supabase: настройка собственного окружения

В репозитории нет действующего проекта Supabase, его адреса или ключей. Создайте своё окружение и заполните локальную конфигурацию. Основной сервер использует REST API; Python SDK Supabase не требуется.

## Схема

SQL-файлы находятся в `tools/`. На новом проекте применяйте их в таком порядке:

1. `supabase_schema.sql` — лицензии, активации и RPC.
2. `supabase_add_tier.sql` — тарифы lite/pro и соответствующая логика лицензий.
3. `supabase_web_users.sql` — веб-аккаунты и их JSON-пресеты.
4. `supabase_auction_data.sql` — снимки аукциона для веб-клиента.

На существующей базе сначала сопоставьте текущую схему со скриптами и сделайте резервную копию. Автоматической миграции рабочей базы при старте нет.

| Таблица | Что хранит |
| --- | --- |
| `licenses` | Хэши ключей, срок действия, тариф и лимит активаций |
| `activations` | Привязки лицензий к HWID или веб-аккаунту |
| `web_users` | Email, хэш пароля, тариф и JSON-пресеты |
| `auction_data` | Регион, JSON-снимок предметов и время обновления |

Проверьте RLS и права в своём проекте: anon должен читать только разрешённые данные аукциона и вызывать предусмотренные лицензионные RPC. Доступ к аккаунтам и запись снимков выполняет админский сервер с `service_key`. Проверьте ограничения таблиц и RPC перед открытием своего сервиса.

BoE-варианты передаются в существующем `auction_data.items_json`, параметры пресетов — в `web_users.presets`. Для нынешних BoE-фильтров и черновиков отдельная миграция не нужна.

## Админская конфигурация

```powershell
Copy-Item supabase_config.example.json supabase_config.json
```

В локальном файле заполните `supabase_url`, `anon_key` и `service_key`. Последнее поле — привилегированный ключ: его нельзя помещать в Git, статические файлы или пользовательскую сборку.

В `.env` отдельно задайте `PUBLIC_ORIGIN`, Blizzard API и при необходимости параметры аналитики. Админский сервер читает `supabase_config.json` для аккаунтов, публикации снимков и выдачи клиенту публичных настроек.

## Конфигурация пользовательской лицензии

```powershell
Copy-Item public_config.example.json public_config.json
```

Этот файл может содержать только `supabase_url` и `anon_key`. Не копируйте в него админский файл целиком. Приложение и подготовка релиза отвергают посторонние поля, `service_role` JWT и ключи с префиксом `sb_secret_`.

Альтернатива для запуска из исходников — переменные `SUPABASE_URL` и `SUPABASE_ANON_KEY`; они имеют приоритет над публичным файлом. `license_manager.py` не читает админский `supabase_config.json`. При отсутствии публичной конфигурации активация возвращает `Supabase not configured`, а не обращается к чужому проекту.

Готовый USER-релиз содержит отдельный `public_config.json`. Админский конфиг и `.env` в него не копируются.

## Лицензии

После настройки своего админского окружения:

```powershell
python generate_license.py --days 30
python generate_license.py --tier lite --days 30
python generate_license.py --permanent
```

Команда записывает лицензию в ваш Supabase и выводит ключ. Ключи, хэши лицензий и файлы `keys_*.txt` являются локальными данными; не добавляйте их в репозиторий.

## Проверка подключения

На тестовой установке проверьте чтение снимка публичным клиентом, невозможность чтения `web_users` с anon key, вход временного аккаунта, сохранение временного пресета и активацию тестовой лицензии. Удалите только созданные для проверки записи. Офлайн-тесты не подтверждают доступность, квоту и права вашего облачного проекта.

Если облако недоступно, черновики пресетов остаются локально. Коллектор повторяет небольшую проверку и отправляет полный актуальный снимок после восстановления; частичный снимок во время сбора не публикуется.
